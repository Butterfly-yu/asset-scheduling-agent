# 复盘

## 最难的问题

最难的是准确处理模型建议、人工授权和数据库写入之间的状态变化。初版真实冲突轨迹中，模型查到备选后尝试调用保存。保存工具拒绝了改期，但模型仍多发起了一次调用。后续把可用工具与已观察到的业务状态绑定，并在每次调用前复核权限。回归测试覆盖模型在同一回复中两次请求保存的情况，首次保存失败后，第二次调用同样不会进入存储层。

人工确认带来另一个问题。生成提案时空闲的时段，在用户确认前可能被其他请求占用。提案因此保存在独立记录中。确认时重新审核并在事务内检查占用，只有事务提交后才返回草稿 ID。确认前抢占的样例得到 `SLOT_TAKEN`，数据库仍为零草稿。 [抢占场景](../examples/mock/stale-confirmation.output.json) · [确认快照](../examples/live/confirmation.db.json)

## 学习收获

1. **从可观察的失败确定下一轮改动。** 历史轨迹暴露了多余保存调用，随后将工具权限细化到业务状态和单次调用，并用构造的重复调用回归验证。
2. **分别表达运行状态和业务状态。** 核对题目后发现，最后一次调用可能已经提交草稿，同时 Agent 的预算已经用尽。输出分别报告未完成的运行和已保存的草稿，重放复用原回执。
3. **把评估落到工具动作和真实结果。** 一次早期真实运行完成了备选查询，却未通过最终输出格式检查。评测因此保留动作判定和业务判定，并使用 SQLite 快照核对写入，便于定位问题出在决策、输出还是存储。 [评估设计与失败记录](03-evaluation.md)

## 下一步

- 扩充真实评测数据，加入不同素材、渠道、时区、无候选和批次部分成功等组合。记录各场景的运行次数、动作通过率与业务通过率。
- 针对最终回复格式失败增加样本，测试更严格的结构化响应校验，并复查是否会影响已有工具调用路径。
- 如果业务需要跨日或时间区间调度，先定义窗口、时区和冲突语义，再扩展候选生成和事务内占用校验。

当前项目使用合成规则和离散时点，候选限于同日向后 1–3 小时。自然语言时间解析、任意区间、外部日历、账号权限和真实发布在当前范围外。 [范围说明](01-requirements.md)

## 用时记录

初版从创建首批项目文件到保存离线测试日志约 10 分钟，按文件时间戳估算。一轮后续实现从创建工作副本到完成真实场景验证约 15 分钟。这两段是有记录的工具执行区间。候选人个人实际投入和项目总用时尚无完整记录。
